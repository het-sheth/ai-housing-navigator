# Live data and deployment path for the Lanark prototype

Research checked September 26, 2026. Scope: the existing single-parcel React/Vite demonstration and the five named public evidence connectors. This is an implementation recommendation, not deployment authorization. The app currently has one bounded browser-side assessment refresh; comparison findings still use dated research snapshots.

## What is verified, and what is not

The [local evidence manifest](../../../ai-housing-hackathon-wiki/docs/evidence/lanark-2026-09-26/manifest.json) and [Lanark evidence note](../../../ai-housing-hackathon-wiki/docs/lanark-evidence-2026-09-26.md) record successful September 26 exact-parcel and polygon queries. The current [assessment adapter](../../src/assessment.ts) only requests `PARID`, `MUNIDESC`, `USEDESC`, `LOTAREA` and `ASOFDATE` for `0023C00208000000`; it checks a single City record and reports a live observation separately from the snapshot. Its tests prove parsing and failure handling with controlled responses. They do not prove production network access.

The research agent attempted a fresh, whitelisted assessment GET from this environment on September 26 which failed before HTTP with `Temporary failure in name resolution`. The web reader could open indexed provider pages but could not open the parameterized WPRDC or ArcGIS service URLs. That isolated agent run did not establish a current parcel result or response headers. The orchestrator subsequently verified the browser-side assessment request from localhost at 18:07:42 UTC on September 26: VACANT LAND, 1,657 sq ft, ASOFDATE 2026-09-01. Browser fetch and parsing succeeded from this local origin. Deployment-origin CORS, current City layer versions and future service availability remain unverified. A successful source lookup from the research screen is dated evidence, not a guarantee of a future request. Recheck the live request and actual response headers in the deployment environment before labeling a connector ready.

[CKAN DataStore documentation](https://docs.ckan.org/en/2.12/maintaining/datastore.html) supports bounded `datastore_search` requests with a resource ID, exact `filters`, selected `fields` and a `limit`. [Esri's map-layer query reference](https://developers.arcgis.com/rest/services-reference/enterprise/query-map-service-layer/) and [feature-layer query reference](https://developers.arcgis.com/rest/services-reference/enterprise/query-feature-service-layer/) support polygon geometry, `inSR`, `spatialRel=esriSpatialRelIntersects`, selected `outFields` and JSON responses. Those are API capabilities, not proof that the named hosts will serve this app in a browser.

## Recommended thin architecture

Keep the current snapshot flow for the next local demonstration. It is deterministic and works without a live source or model. Label it `September 26, 2026 research snapshot`; allow the existing assessment refresh to add a separate observation with its own `ASOFDATE`, retrieval time and failure status. A failed or empty request must never mean no zoning, no slope or no permits. The assessment and permit conflict remains a finding until independently reconciled.

For a live multi-source iteration, add a small same-origin endpoint rather than arbitrary URL forwarding. It should accept only an exact parcel identifier from an allowlist at first, query each named provider with fixed field whitelists and size/time limits, validate jurisdiction, record source/retrieval dates, and return independent `live`, `unavailable` or `unsupported` states per connector. Keep geometry and rule evaluation separate: use the complete parcel polygon and explicit EPSG:2272 for ArcGIS queries, then retain the original source attributes and conflicts. A backend is necessary if the named services reject cross-origin browser requests, if response normalization needs one trusted boundary, or if provider credentials are later needed. The assessment fetch works from the tested localhost origin; cross-origin behavior for other providers and the eventual deployed origin remains unverified. Do not add a general proxy or infer legal permission from joined data.

A model call, if later justified for unstructured proposal input, must use a server endpoint with provider credentials stored server-side. It should return bounded structured fields with explicit unknown outcomes for user confirmation. The deterministic rule engine owns joins, arithmetic and conditional code checks. No provider, account, budget or domain performance has been verified; the present app correctly labels AI unavailable. Hosting credentials must never enter Vite `VITE_` variables or browser code. [Vercel environment variables](https://vercel.com/docs/environment-variables) and [Cloudflare Pages secret bindings](https://developers.cloudflare.com/pages/functions/bindings/) both provide runtime server-side storage options, subject to account setup.

## Hosting options, proposed only

| Option | Fit for this app | Main tradeoff |
| --- | --- | --- |
| [Vercel Vite deployment](https://vercel.com/docs/frameworks/frontend/vite) with [Node.js functions in `api/`](https://vercel.com/docs/functions/runtimes/node-js) | The existing Vite build can be hosted as static assets, with a later small Node API in the same project. This is the simplest proposed path if a Node-only model SDK is eventually chosen. | Provider-specific function conventions and environment configuration must be tested locally and in preview before production. No account or deployment has been configured. |
| [Cloudflare Pages for React](https://developers.cloudflare.com/pages/framework-guides/deploy-a-react-site/) with [Pages Functions](https://developers.cloudflare.com/pages/functions/get-started/) | Builds with `npm run build` and `dist`; a `/functions` directory can add same-origin endpoints. Good fit for fetch-only public-source adapters. | Functions run on the Workers runtime with only a subset of Node APIs unless compatibility is configured. Test any future model SDK before choosing this path. |

Recommendation: keep the app host-neutral while it is a local snapshot prototype. If deployment is separately authorized before model choice, Vercel is a pragmatic first preview because the future server boundary can use Node without SDK compatibility work. Cloudflare Pages is equally plausible for static UI plus fetch-based adapters. This is an engineering inference from the cited runtime docs, not a cost, reliability or account comparison. No price or quota claim is made.

## Publish and live-data gate

1. Obtain separate authorization for a remote repository and preview deployment; neither is currently authorized by the app instructions.
2. Confirm parcel, zoning and slope reuse terms for the exact assets to be bundled or displayed publicly; preserve PLI attribution and WPRDC terms.
3. Exercise exact-PARID and whole-polygon requests from the selected host and a real browser. Record status, CORS response headers, field schemas, provider errors, request duration, retrieval time and source version where available. Keep the snapshot if any connector fails.
4. Verify current zoning code dependencies and City interpretation before public parcel-specific entitlement claims. Keep the assessment/permit conflict, slope limitations, flood and historic unknowns visible.
5. Test a preview's case-to-comparison-to-export flow and failure states. Confirm the export identifies which facts are September 26 snapshots and which, if any, are later live observations.
6. For a judged hackathon submission, resolve the organizer's score-format expectation and obtain at least bounded practitioner feedback on the workflow. The component-only overall `not rated` state and practitioner fit remain open gaps, not validated claims.
